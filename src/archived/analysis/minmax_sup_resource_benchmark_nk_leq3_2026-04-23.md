# `Sup x Max_f` Resource Benchmark: Patched Main-Repo vs Threshold-Extremal (`n,k <= 3`)

Date: 2026-04-23

## Scope

This note reports the resource-consumption benchmark comparison between:

- the patched copied main-repo backend in
  [NestedAutomaton_mainRepo_sup_max_compare.cpp](./NestedAutomaton_mainRepo_sup_max_compare.cpp)
- the live threshold-extremal backend in
  [src/NestedAutomaton.cpp](/home/ege/Desktop/QuAK-playground%20%2828.01.26%2015%E2%88%B612%29/src/NestedAutomaton.cpp:5928)

for:

- `isNonEmpty(Sup, Max_f, k)`

on the generated family:

- `samples/generated_resource_consumption/resource_n{n}_k{k}.txt`

with:

- `1 <= n <= 3`
- `1 <= k <= 3`

The measurement probe is:

- [minmax_sup_resource_probe_compare.cpp](./minmax_sup_resource_probe_compare.cpp)

## What The Benchmark Family Is

The family is generated by:

- [samples/nwa_gen_resource.py](/home/ege/Desktop/QuAK-playground%20%2828.01.26%2015%E2%88%B612%29/samples/nwa_gen_resource.py:158)

There is also a fuller family description in:

- [resource_consumption_family_description.md](./resource_consumption_family_description.md)

For each pair `(n, k)`, the generator builds:

- one one-state final parent `q0`
- one real child per process `i in {1, ..., n}`
- one dummy `@CHILD 0` for silent parent edges

The alphabet contains:

- start symbols `s1, ..., sn`
- terminate symbols `t1, ..., tn`
- resource-use symbols `a{i}_{j}` for process `i` and resource `j`

Child `i` is a deterministic tracker with:

- `init_i`
- one tracking state for each subset of the `k` resources
- `rej_i`
- `acc_i`

So each real child has:

- `2^k + 3` states

The intended behavior is:

1. `s_i` starts a call to child `i`
2. letters `a{i}_{j}` mark which resources of process `i` have been used
3. `t_i` terminates the child and returns the number of distinct resources seen

The benchmark query always uses:

- `threshold = k`

So each instance is positive: the word

```text
(s1 a1_1 a1_2 ... a1_k t1)^\omega
```

already yields child return value `k` infinitely often.

This family is therefore not a yes/no separator. It is a stress test for:

- flattening cost
- state-space blow-up
- memory footprint

## Example Instance

Example:

- [samples/generated_resource_consumption/resource_n2_k2.txt](/home/ege/Desktop/QuAK-playground%20%2828.01.26%2015%E2%88%B612%29/samples/generated_resource_consumption/resource_n2_k2.txt:1)

The file starts like this:

```text
@PARENT
final: all
# Single-state parent: on s_i it calls child i, otherwise SILENT.
final: q0

s1 : 1, q0 -> q0
s2 : 2, q0 -> q0
t1 : 0, q0 -> q0
t2 : 0, q0 -> q0
a1_1 : 0, q0 -> q0
a1_2 : 0, q0 -> q0
a2_1 : 0, q0 -> q0
a2_2 : 0, q0 -> q0

@CHILD 0

@CHILD 1
final: acc1

s1 : 0, init1 -> track1_0
s2 : 0, init1 -> rej1
t1 : 0, init1 -> rej1
t2 : 0, init1 -> rej1
a1_1 : 0, init1 -> rej1
a1_2 : 0, init1 -> rej1
a2_1 : 0, init1 -> rej1
a2_2 : 0, init1 -> rej1

# Tracking state track1_0: mask=0
t1 : 0, track1_0 -> acc1
a1_1 : 0, track1_0 -> track1_1
a1_2 : 0, track1_0 -> track1_2
```

Child `2` is symmetric. The hardness comes from the flattener needing to reason
about many active calls across multiple process-local subset trackers.

## What Was Measured

For each instance and each backend, the probe measures:

1. flattened automaton size:
   - `states`
   - `transitions`
2. total answer time:
   - wall-clock time from before flattening to after
     `removeSilentTransitions(..., Sup, false)` and
     `isNonEmpty_withFinal(Sup, 1)`
3. memory:
   - `peak_rss_kb`
   - `rss_delta_kb`

Important detail:

- each benchmark row was run in a fresh process

So the RSS numbers are meaningful per-instance measurements, not cumulative
artifacts from a long in-process loop.

## Discussion

### 1. Tiny cases are close

For `n = 1`, the two backends are still in the same rough ballpark.

- At `n=1,k=1`, they have the same number of states.
- At `n=1,k=2` and `n=1,k=3`, the patched backend actually has fewer states.

But even there, the patched backend already has:

- more transitions
- higher total runtime

So state count alone is not telling the whole story.

### 2. Once `n >= 2`, threshold-extremal is clearly smaller

From `n=2` onward, the threshold-extremal backend is better on:

- states
- transitions
- runtime
- memory

Examples:

- `n=2,k=2`
  - states: `332` vs `176`
  - transitions: `2750` vs `958`
  - time: `38.1ms` vs `12.7ms`
  - peak RSS: `9.6MB` vs `6.6MB`
- `n=3,k=2`
  - states: `8012` vs `3244`
  - transitions: `99105` vs `24957`
  - time: `1574ms` vs `313ms`
  - peak RSS: `188MB` vs `60MB`

### 3. Transition blow-up is especially severe in the patched backend

The largest gap is often not state count but transition count.

Representative cases:

- `n=3,k=1`
  - states: `1320` vs `424`
  - transitions: `12417` vs `2328`
- `n=3,k=3`
  - states: `54996` vs `25300`
  - transitions: `844197` vs `263520`

So the patched backend is not just reaching more global states. It is also
materially denser.

### 4. Memory tracks the same pattern

The RSS numbers follow the same growth trend as states and transitions.

The clearest case is the hardest solved instance:

- `n=3,k=3`
  - patched peak RSS: `1600520 KB`
  - threshold-extremal peak RSS: `547848 KB`

So the patched backend uses roughly:

- `~1.60 GB` vs `~0.55 GB`

on that case.

### 5. Runtime gap grows into seconds, not just milliseconds

The largest solved case shows the practical difference most clearly:

- `n=3,k=3`
  - patched: `15611.9 ms`
  - threshold-extremal: `4378.3 ms`

That is:

- about `15.6s` vs `4.4s`

So even after the correctness fixes, the patched backend remains much more
expensive on this family.

## Interpretation

This matches the structural difference between the two approaches.

The patched main-repo backend is still based on:

- explicit activation/tracking bit-vectors over flattened child-state space
- one distinguished witness token
- recursive per-state/per-symbol propagation

The live threshold-extremal backend uses:

- threshold-extremal obligation bags
- a more compact global representation of what still matters for the threshold

So the patched backend can be fixed to match the live path on correctness
without becoming competitive on this benchmark. The correctness patch removed
false negatives and false positives, but it did not change the underlying
state-space model enough to close the performance gap.

## Bottom Line

On the `resource_n{n}_k{k}` family for `n,k <= 3`:

- the patched copied backend matches threshold-extremal on the tested answers
- but threshold-extremal is consistently better once the instances get beyond
  the tiny `n=1` regime

The biggest solved case, `n=3,k=3`, summarizes the tradeoff:

- correctness: same answer
- flattened size:
  - `54996 / 844197` vs `25300 / 263520`
- total time:
  - `15.6s` vs `4.4s`
- memory:
  - `1.60GB` vs `0.55GB`

So the patched backend is now a correctness-aligned reference for this `Sup/LimSup x Max_f`
slice, but it is still not the performance-preferred implementation.
