# Resource-Consumption Benchmark Family

Date: 2026-04-23

This note describes the nested-automaton family generated by:

- `samples/nwa_gen_resource.py`

and benchmarked for the recent `Sup x Max_f` comparison.

The completed `n,k <= 4`, `120s` run is saved in:

- `results/minmax_sup_resource_small_n4_t120.csv`

The earlier aborted `n,k <= 5`, `30s` run is saved in:

- `results/minmax_sup_resource_small.csv`

The three compared Sup-Max implementations are collected in:

- `analysis/minmax_sup_compared_implementations.cpp`

## 1. High-Level Shape

For each pair `(n, k)`, the generator builds one nested automaton with:

- one parent process
- `n` nontrivial children, one per process
- one dummy `@CHILD 0` used for silent parent edges

The intended reading is:

- `n` = number of processes
- `k` = number of resources available to each process

The family is generated by:

- `alphabet_symbols(...)` in `samples/nwa_gen_resource.py:21`
- `emit_parent(...)` in `samples/nwa_gen_resource.py:43`
- `emit_child_i(...)` in `samples/nwa_gen_resource.py:76`
- `generate_resource_consumption_automaton(...)` in
  `samples/nwa_gen_resource.py:158`

## 2. Alphabet

The alphabet has three kinds of symbols:

1. start symbols:
   - `s1, s2, ..., sn`
2. termination symbols:
   - `t1, t2, ..., tn`
3. resource-access symbols:
   - `a{i}_{j}` for process `i` and resource `j`

So the alphabet size is:

- `n + n + n*k = n(k + 2)`

Examples:

- `(n=2, k=2)` has `8` symbols:
  - `s1 s2 t1 t2 a1_1 a1_2 a2_1 a2_2`
- `(n=3, k=2)` has `12` symbols

## 3. Parent Automaton

The parent is intentionally tiny:

- one state: `q0`
- `q0` is final
- every transition loops back to `q0`

Semantics:

- on `s_i`, the parent invokes child `i`
- on every other symbol, the parent takes a silent transition

So the parent contributes almost no control complexity by itself.

This is visible in `emit_parent(...)`:

- `s_i : i, q0 -> q0`
- `t_i : 0, q0 -> q0`
- `a{i}_{j} : 0, q0 -> q0`

The whole difficulty is therefore pushed into:

- the child automata
- and the flattening algorithm’s representation of many simultaneously active child calls

## 4. Child `i`

Each nontrivial child is a deterministic resource tracker for process `i`.

Its state space is:

- `init_i`
- one tracking state for each subset of the `k` resources
- `rej_i`
- `acc_i`

So child `i` has:

- `1 + 2^k + 1 + 1 = 2^k + 3` states

This is explicitly documented in `emit_child_i(...)`.

### 4.1 First-letter discipline

When child `i` is spawned, it must immediately consume `s_i` as its first input.

From `init_i`:

- `s_i` goes to `track{i}_0`
- every other symbol goes to `rej_i`

This is the “same-symbol consumption” convention noted in the generator header.

### 4.2 Tracking region

After consuming `s_i`, the child stores which of its own resources have been seen.

Tracking states are named:

- `track{i}_{mask}`

where `mask` is a bitmask in `[0, 2^k - 1]`.

Interpretation:

- bit `j-1` is `1` iff resource `j` of process `i` has been accessed

### 4.3 Behavior inside tracking states

From `track{i}_{mask}`:

- seeing `a{i}_{j}` updates the bitmask by setting bit `j`
- seeing `t_i` terminates the child and goes to `acc_i`
- seeing `s_i` again goes to `rej_i`
- every symbol belonging to a different process is ignored with weight `0`

This gives the child a strong local/process-specific behavior:

- it only really cares about:
  - `s_i`
  - `t_i`
  - `a{i}_{1}, ..., a{i}_{k}`
- everything for other processes is a self-loop with weight `0`

### 4.4 Returned weight

The key quantitative action is the first `t_i`.

On `t_i`, the child returns:

- `popcount(mask)`

That is:

- the number of distinct resources of process `i` seen since the call began

So child return values range over:

- `{0, 1, ..., k}`

and the maximum possible child return is exactly:

- `k`

## 5. Dummy Child 0

`@CHILD 0` is the silent/dummy child.

Its purpose is only:

- to support silent parent edges in the parser/flattening setup

It does not carry the benchmark difficulty.

## 6. Why This Family Is Always Positive For `Sup x Max_f`

In the benchmark, the query threshold is chosen as:

- `threshold = k`

for instance `resource_nX_kY.txt`.

For `Sup x Max_f`, this asks whether there exists an infinite word whose sequence
of child-return values has supremum at least `k`.

That is always possible here.

Example witness word for process `1`:

```text
(s1 a1_1 a1_2 ... a1_k t1)^\omega
```

Each cycle:

1. spawns child `1`
2. accesses all `k` resources of process `1`
3. terminates with return value `k`

So:

- `Max_f = k` on each completed child call
- hence `Sup = k`
- therefore the nonemptiness query at threshold `k` is true

This matches the raw benchmark CSV:

- every solved row has `result=1`

So this benchmark is not about separating YES from NO instances.
It is about:

- how expensive the construction/checking path becomes before it can certify the
  obvious positive witness

## 7. What Actually Makes The Family Hard

The benchmark stress does **not** come from a complicated parent.
It comes from the interaction of three growth axes.

### 7.1 Exponential local child state space

Each child has:

- `2^k + 3` states

because it explicitly represents all subsets of seen resources.

So increasing `k` doubles the size of the local tracking region.

### 7.2 Many simultaneously relevant process types

There are `n` different children.

Since child `i` ignores symbols of other processes, a word can keep many
cross-process invocations “alive” for a long time.

That means the flattening algorithm must reason about combinations of:

- different processes
- each in different resource-subset states

### 7.3 Large total alphabet with many process-local no-op letters

The alphabet size is:

- `n(k+2)`

and most letters are irrelevant to any fixed child.

That sounds harmless, but for an explicit flattening it means:

- every active child state still has to be stepped on every symbol
- most of those steps are “ignore and stay”
- the flattening still has to represent and propagate them

This is especially painful for explicit/global-state-style constructions.

## 8. What The Checked-In Instances Look Like

Concrete examples:

- `samples/generated_resource_consumption/resource_n2_k2.txt`
- `samples/generated_resource_consumption/resource_n3_k2.txt`

Example `(n=2, k=2)`:

- parent has one state `q0`
- children `1` and `2` each have `2^2 + 3 = 7` states
- resource subsets are:
  - `00`
  - `01`
  - `10`
  - `11`
- terminating in subset `11` returns weight `2`

Example `(n=3, k=2)`:

- same parent shape
- now there are three resource-tracking children
- each child still has `7` states
- alphabet grows to `12` symbols

## 9. Important Small Repository Quirk

The generator source currently describes the intended parent as:

- one final state `q0`

but the checked-in generated files still show an extra stale line:

- `final: all`

before:

- `final: q0`

The intended structure is the one in `samples/nwa_gen_resource.py`.
The benchmark interpretation above uses that intended structure.

## 10. Why The Family Hurt `split_witness`

The original motivation of split-witness was local:

- keep the old-v2 explicit-construction idea
- avoid introducing a full multiset of child invocations into each state

That design goal is documented in:

- `analysis/old_v2_minmax_sup_overlap_merge_issue_2026-04-22.md`
- `analysis/minmax_sup_change_log.md`

But on this family, the dominant cost turned out to be:

- explicit recursive enumeration of many active background states
- plus very large transition fanout

This shows up clearly in the results.

Examples from `results/minmax_sup_resource_small_n4_t120.csv`:

- `(n=3, k=3)`
  - `threshold_extremal`: `25,300` states, `263,520` transitions, `4.28s`
  - `regular`: `73,743` states, `652,236` transitions, `14.28s`
  - `split_witness`: `64,500` states, `986,757` transitions, `23.81s`
- `(n=4, k=2)`
  - `threshold_extremal`: `51,616` states, `519,188` transitions, `9.77s`
  - `regular`: `131,981` states, `1,171,000` transitions, `27.19s`
  - `split_witness`: `199,236` states, `3,258,044` transitions, `90.06s`

So the main failure mode was:

- split-witness did **not** stay compact enough in the global graph
- and in several cases it paid much more in transition count than even regular

In other words:

- the witness/background split avoided one kind of representation blow-up
- but this family exposed a different one: explicit branching and propagation
  cost over a huge alphabet and many active subset-tracking child states

## 11. Practical Reading Of The Family

If you want a short mental model, this benchmark is:

- a one-state scheduler
- repeatedly launching process-local monitors
- where each monitor counts how many distinct local resources it has seen before
  termination

The benchmark gets harder when:

- there are more processes to interleave (`n` grows)
- each process has more local resource subsets to remember (`k` grows)

That combination makes it a good stress test for:

- explicit flattening strategies
- obligation compaction
- and global-state explosion under many mostly-irrelevant letters
